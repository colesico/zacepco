== About the Document

This document describes the mechanics of the detective game and sets the general rules by which it should be built.  
An integral addition to these mechanics for the completeness of the game are *crime scripts*, which describe the plot component.  
The mechanics themselves are essentially a *framework* for a deductive detective game with elements of randomness.

== Crime Script

Within the mechanics, a script describes a crime that has *already occurred*.  
During the game, the players (detectives) must solve this crime.  
A script targets varying degrees of difficulty in solving a crime, describing, for example, one crime or several at once, involving one or several criminals, with or without accomplices, with different numbers of suspects, crime duration, size of the "theater of operations," etc.

Any script contains:

* Instructions for preparing for the start of the investigation.
* Information for the course of the investigation.
* An "Answers" section that can be viewed at the end of the game.

Ready-made scripts come with the game or are generated by a special program.

The game follows the script chosen by the players and is divided into two *phases*.

In the first phase, according to the script, players perform preparatory actions to start the investigation: assembling the game board, etc. 
This phase essentially recreates the initial picture of the committed crime for the players.

The second phase is the investigation, a cooperative process of solving the crime by the detectives.

At the end of the game, the investigation's conclusions are compared with the answers from the script.

== Master Program

To moderate the game process, a computer program is used — the *"Master Program"*, which is configured by the script for a specific game.  
The program also automates all calculations related to the gameplay and controls the game mechanics.

== Game Entities and Connections

The script operates with the following types of *game entities*:

* *Personage ( P )* — an actor in the crime;
* *Location ( L )* — a part of the crime scene;
* *Clue ( C )* — a piece of information about the crime;
* *Time ( T )* — a moment in time during the crime (tick).

The game entities themselves (except for time) are represented by entity cards.  
Each such card has its own format depending on the entity type.  
An entity is identified by a unique identifier starting with a letter corresponding to the entity type, followed by the unique entity code. 

====
For example, P2, LLIB, CKEY.
====

Time does not have its own cards, only a sequence number (T1, T2, …) and a timestamp binding.

Each of the game entities can be linked by the script to any other entities.  
From the perspective of a connection, when one entity refers to another, the first is called the *key entity*, and the second is called the *target entity*.

The script defines a set of game entities and their connections, which essentially describes the crime (defines the crime model).

Some of these entities and connections may be unrelated to the crime and serve to complicate the investigation process (falsity clues).

Before the investigation begins, a small portion of the entities and their connections is known to the detectives.  
During the investigation, the detectives gradually discover the remaining entities and connections.

In general, the mechanics assume that entity cards require self-manufacturing (printing) before the game. 
The Master Program can generate their print layouts from the script. 

Printing all cards is not mandatory; some cards in the script may be borrowed from other scripts. Such cards are called *reference* cards, and the script contains notes on which scripts these cards can be taken from.


== Discovering Entities and Connections

The game uses a mechanic of *step-by-step* discovery of entity cards and detection of connections between them by detectives.

Based on certain already discovered key entities, detectives can learn their connections to other target entities, both discovered and not yet discovered.  
Then they can choose other key entities and determine the next target entities and connections based on them, and so on.

Connections between entities are revealed through the *discovery* of clues. 
The method for discovering specific clues is defined by the script as a specific game mechanic.

To avoid revealing all the information about the crime to the detectives at once, the *Master Program* is used for step-by-step information delivery.

== Element of Randomness

D12 dice.

== Resource, Points

In the game, each action by a detective costs a certain amount of *resource*.  
If an action is successful, the player is awarded *points*.  
The script defines the total resource *budget* for the investigation.  
When the budget is exhausted, the investigation stops, and the detectives must draw conclusions based on the available data and compare the results with the script's answers.

When initializing the investigation in the Master Program, players can increase or decrease the initial budget by a certain percentage, giving themselves an additional advantage or challenge.

The individual number of points earned determines the best detective in the investigation, provided that the detectives solved the crime. If the detectives failed to solve the crime, the points earned are not counted.

== Game Time

A crime script spans a period of time divided into *ticks* (`T1, T2, … Tn`) — equal or unequal time intervals.

Each tick has a timestamp (date-time), for example, `T4 = 21:30`. The timestamp sets the *right boundary* of the tick. Events of `T4` occur after the timestamp of the previous tick and no later than `21:30`. The script contains a publicly accessible "Timeline" table, in which each tick is assigned a timestamp.
The difference between adjacent timestamps must be plausible: within a tick, a personage must have enough time to perform the actions implied by the script.

All significant events of the crime occur in specific ticks; clues are bound to tick timestamps rather than to time values within the tick itself. Even if, for example, for T3 = 21:00 and T4 = 21:30, a clue indicates the time 21:20 — the event is considered to have occurred in tick T4, regardless of when exactly within the tick it happened. The exact order of events within a tick is undefined and not used for deduction, i.e., all events within a tick are consistent from the perspective of clues.

The more ticks there are, the harder it is to solve the crime.

== Crime Scene, Locations, Connections

In the script, the crime scene is defined as a graph.  
In the preparation phase for the investigation, based on this graph, players assemble the crime scene — the *scene* — from individual *locations* (graph nodes). The scene is a grid of a specific size. The grid size is defined by the script. A location is placed in any cell of the scene grid. Some cells of the scene may be left empty.

Each location is represented by a square location card (reference or custom). A location card contains the following information:

* ID;
* Name;
* Description;
* Location image.

Two adjacent locations can be connected by *ways*, which determine the possibility of a personage moving between them.  
If two non-adjacent locations need to be connected, way cards of various configurations (straight, turn) are used, laid out one after another in empty cells of the scene to connect the required locations.  
A way always connects only two locations. Two locations can be connected by only one way.

In the script, restrictions or characteristics of a way for movement can be specified as a *description*. For example: a river 10 meters wide. If there is no way description, it is assumed that only the fact of being able to move from one location to another is important for the investigation, and the conditions for this movement are not.

Nothing ever happens to personages on the way itself;  
if any actions of a personage in transit need to be modeled, the way is replaced by a full-fledged location.

The script may also assume the presence of *"hidden"* ways between locations that are initially invisible to the detectives.  
Detectives learn about the existence of such ways during the investigation.  
When a clue revealing a hidden way is discovered, the card for this way is also placed on the scene.

A hidden way can lead to a *hidden location*.  
This is a location that the detectives do not know about before the investigation begins.  
When a clue that reveals a *hidden way and a hidden location* is discovered, the hidden location card is placed on the scene at the spot specified in the script, along with the way leading to it.
Once discovered, the location becomes available for investigative actions.

Information about all hidden ways and locations is available in the script's *answers*.

When developing a script, locations and way descriptions should be defined in such a way that their meaning in the investigation is taken into account.  
For example, there may be no light in a cave, a personage can enter the basement only with a key, a poisonous plant may grow in the greenhouse, a bar operates from the 3rd to the 6th tick, etc.  
The semantic load and description of locations and ways should assist detectives in the investigation.

For each location, the script describes an event *log* of that location for each time tick.  
A log entry contains information about which personages had this location as their *target* during the tick, and which clues appeared in the location.

The event log is used at the end of the game as answers when checking the investigation's conclusions and is unavailable to players during the investigation.

== Personages

An actor in the crime is a *personage*.  
Each personage is represented by a (reference or custom) personage card.  
A personage card contains the following information:

* ID;
* Name;
* Dossier (description);
* Personage image.

The set of personages in the game is defined by the script.  
The script specifies explicit personages — they are known before the investigation begins.  
Their cards are laid out next to the game board.

The script may also use *hidden personages*.  
A hidden personage is one whose card has not yet been placed face-up on the table from the personage deck.  

The presence of a hidden personage can be determined during the investigation logically, based on discovered clues, or upon discovering a clue that reveals the hidden personage (similar to clues pointing to a hidden way or location).  
When a clue revealing a hidden personage is discovered, their card is placed face-up next to the game board alongside the cards of the other personages.  
After this, the personage becomes available for investigative actions.

Hidden personages can be learned about in the script's answers.

Personages in the script should be described in such a way that this description helps detectives in the investigation.

== Personage Movements and Actions

The mechanics separate the concepts of *movement* and *action*.
For each personage during the crime, *in each tick* of time Ti, there is only one of the following alternatives:

* Remain in the current location and do nothing.
* Remain in the current location and then perform *one* *action*.
* Move to an adjacent location and do nothing.
* Move to an adjacent location and then perform one *action*.

Movement occurs to an adjacent location if they are connected by a *way*.  
The script may impose restrictions on a way, such as a door that must be unlocked with a key (specified in the way description).  
In general, a personage can visit the same location multiple times in different ticks.  
For easier game variants, a personage may visit a location only once.

A personage's movement track (sequence of locations) is implied by the script, but is not explicitly revealed to the players.  
Players can determine this track during the investigation.

Personage tracks are revealed by the script as "answers": for each personage, their movements are indicated as a sequence of location IDs for each tick (in the personage's log).  
This information can be viewed at the end of the game.

During the investigation phase, various methods can be used to visualize the suspected movement path (*track*) of a personage on the game board — tokens placed on locations, notes on paper, etc.

While in a *target* location, a personage can perform *one* action. The mechanics do not provide for the action itself as an entity, but the result of this action is *clues* (one or more), which are linked to the location, to personages, or to examination.

==== 
For example: 

* A personage saw another personage somewhere. The first personage receives a clue in the form of witness testimony, which can be uncovered during interrogation.

* One personage killed another personage. The murdered personage receives a clue — "Personage is dead." The murderer receives — "Bloodstains on clothes."
====

For each personage, the script describes an event *log* of that personage for each time tick.  
A log entry contains information about which *target* location the personage was in and which clue was bound to them (for example, they left a trace in the location or a trace remained on the personage).

The event log is used at the end of the game when checking the investigation's conclusions and is unavailable to players during the investigation.

== Clues

A *clue* is a piece of information about the committed crime that detectives sequentially uncover during the investigation.  
A clue can be a physical object, an event, some information, or a fact.

Examples of clues: witness testimony, motive, note, cigarette butt, habit, personage's addiction, the fact that an item is missing from a location, expert report.

The crime script defines the set of clues involved in the game.  
A clue is represented by a clue card with the following printed on it:

* ID;
* Name;
* Description (detailed);
* Clue image.

Whenever possible, clues should not point directly to a suspect — the connection should emerge when compared with other entities. This makes the task more challenging for detectives. In the script, as answers for checking investigation results, the actual entities to which a given clue *leads* can be specified for each clue.

Some clues may be unrelated to the crime and serve to complicate the game (*falsity* clues). The more such clues there are, the harder the game.

Initially, clues are generally hidden from the detectives.  
During the investigation, detectives gradually "discover" clues — laying clue cards face-up. However, the script may mark some clues as initially *discovered* and available to the detectives.

Any clue, upon being discovered, can automatically *reveal* other entities — hidden locations/personages, or other clues. The auto-reveal capability for a clue is defined by the script.

During the crime, clues appear as a result of personages' actions or external factors. 

====
For example:
 
* Due to a power outage in tick T5, the clue "It is dark in the location" appears in location L4, which is recorded in the location's log.
* At some point, poisonous gas appeared in the location. As a result, a personage gets the testimony clue "In L9 at T9, I felt like I was losing consciousness."

====

Sources of clues for detectives are:

* Locations
* Personages
* Examination


=== Location Clues

During the crime, some clues remain in locations. Detectives can uncover them there during the investigation by conducting a search. 

====

Examples of clues in a location:

* Hidden passage to location L4 (Basement)
* C2 (Candlestick) is missing here, although it was originally here
* Broken clock. The hand points to 10:30 (T8)
* Personage P1 (Gardener) was spotted here at 10:30 (T3) with a Knife (CKNF) in hand
* It is dark here

====

=== Personage Clues

Personages, just like locations, can possess certain clues.  
It is assumed that some of them were with the personage before the crime, for example — clothes, personal belongings, character.  

Some clues were obtained by personages during the crime — picked up in locations or received from other personages, for example — a knife, a note, bloodstains.  

Another part describes their inherent traits. For example — habits, alcohol addiction, character, etc. 

The remaining clues are witness testimonies of the personage: what they heard, saw, know about somewhere, etc.  

The script also assumes that during the crime, personages can leave clues in locations, pass them on, or plant them on other personages when meeting them in the same location.

Some of a personage's clues may be known to the detectives before the investigation, for example — clothes, character, etc. Other clues are hidden.

====

Examples of clues on a personage:

* While in the Library (L1), saw the Janitor (P1) in the garden (L4) 
* Smelled burning coming from the Camp (L3)
* I have a bad temper and I love to smoke
* Pocketknife with traces of dirt

====

== Searching a Location or Personage (search)

During the investigation, detectives can *"search"* any open location or personage (including previously hidden ones) to try to discover these clues.

As a result of a search, a clue may be "detected" (discovered) with a certain probability.

To describe the initial picture of the crime, some clues in locations or on personages may be known to the detectives before the investigation. 
The remaining clues are hidden.

====
For example:

* In the library location — open clue: "Cracked safe."
* On personage PVIC, open clue — "Personage is dead."
====

To determine the parameters for discovering clues during a search, the script defines a *"Search"* table.  

Search is implemented through a probabilistic clue detection mechanic combined with the *"Search Focus"* mechanic.  

Focus makes it more likely to detect a clue that the search focus is directed at and earns the detective more points.  
However, the strategic goal of focus is less about "getting" a clue and more about *formulating a hypothesis to test*.  
Focus consists of two parts: the table focus (reference) and the detective's focus.

A search costs a certain amount of resource. A detective can be awarded points for a search.

Search procedure:

1. The detective declares a search of a specific location or personage, for example, L1.
2. Specifies the detective's focus — a set of IDs of any *open* entities or any entity types, in a quantity not exceeding that specified in the script (focus limit).
+
For example: T4, L?, C?.
3. Rolls a D12 dice to model the probabilistic nature of clue detection.
4. The search result is determined using the "Search" table.  
   Access to the search table is provided through the Master Program.


=== Example of a "Search" Table

|===
|Focus           |Threshold|Clue
| P4, L3, L4, T4 |5.2      |C8
| L4, C5, C6     |5.0      |C3
|     L6         |8.0      |C12
|===

----
Clue C8 is linked by the script to personage P1, while C3 and C12 are linked to location L1.
----

[[search-focus]]  
*Focus* — the table search focus. Serves to increase the probability of discovering clues that have connections to the target entities of interest to the detective.  
Only the _IDs_ of entities connected to the target clue are listed in the table focus.  
Specifying individual entity types in the table focus is not allowed.  
Several IDs of the same type can be listed separated by commas — this is interpreted as any one of them.

The detective's focus can consist of one or more IDs of *open* entities or any types of these entities.  
For example: "P1, C1, T?". The maximum number of elements in a detective's focus is defined in the script (usually 1–3).

*Threshold* — the clue detection threshold. A _real_ number that is compared with the roll on the D12 dice.  
If the roll is less than the "Threshold," it is considered that negative factors came into play, and the target clue is not detected.  
In the script, the detection threshold is set so that the clues most important to the investigation have higher threshold values. The ability to specify fractional values allows for "fine-tuning" the ordering of clues.

To reduce the influence of randomness, low threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the ID of the target clue. The card of the detected clue is placed face-up next to the entity where it was found.

=== Search Cost, Point Scoring

[[search-cost]]  
*Search cost* — the resource cost of a search is the same for any entity and is defined in the script.  
Determines how many resources are spent per search. The detective learns the cost at the beginning of the game.

[[search-points]]  
*Search points* — the base number of points that can be awarded to a detective for a search.  
The same base number of points is defined for all entities in the script.  
Base points are awarded for discovering a clue, provided it was _NOT_ *<<accidental-discovery, accidentally discovered>>*.  
When base points are awarded, one additional point is granted for each matching _entity id_ between the detective's focus and the table focus.

== Algorithm for Determining the Target Clue in the Search Table

Goal of the algorithm: to determine the clue that best matches the detective's focus and the D12 roll.

The algorithm considers only the rows of the search table pertaining to the selected entity.  
Rows for which the clue has already been discovered in previous searches are excluded from consideration.

1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus match weights>>).
2. The table rows are sorted by descending "EQ", descending "EQT", ascending "NE", and descending *Threshold*.
3. Sequentially, starting from the first row, the rows are "scanned".
4. If (D12 >= "Threshold") and ( EQ > 0 or EQT > 0 ), the scan stops. The clue is detected purposefully, and it is discovered.  
+
It is reported how many points are awarded to the detective.
+
Matching elements (entities + types) of the _detective's focus_ with the table focus of the discovered clue are reported:

   * Matching entity IDs and types in the detective's focus;
   * ID types of non-matching entities in the _table_ focus.

====
For example, when searching L1 with the detective's focus "P2, T4, C?" and table focus "P1, P2, T4, L2", the output will be:  
"In L1, clue C2 was found, connected to P2, T4, P?, L?".
====

[start=5]
[[accidental-discovery]]  
5. If no matching row is found (the focus does not match or the D12 value is insufficient), an *"Accidental Discovery"* of a clue occurs.  
   The clue with the lowest threshold among those under consideration (not yet discovered clues) is discovered.  
+
It is reported that a suspicious clue was accidentally discovered, without additional information as in the case of purposeful detection.


[start=6]
6. If all clues of an entity are discovered, an "All Clues Discovered" token is placed on the clue. Further searches are impossible.

[[focus-weights-comp]]  
=== Calculating Focus Match Weights

The following focus match weight values are calculated between the detective's focus and the table focus:

* EQ = [number of matching entity IDs in the focuses],
* EQT = [number of matching types in the focuses],
* NE = [number of *NON*-matching entities or types] in the detective's search focus and in the table focus.

First, "EQ" is calculated by comparing IDs in both focuses. Next, matching IDs are excluded from both focuses.  
To calculate "EQT", the entity types explicitly specified in the detective's focus (P?, L?, …) are compared with the types of the remaining entity IDs in the table focus. Elements matched when calculating "EQT" are excluded from both focuses.  
"NE" is calculated as the total number of remaining entities in the focuses.

When calculating "EQT", an element of type "X?" in the detective's focus is considered matched with a table focus entity (with an ID) if type "X?" corresponds to the type in the entity ID.

For example, the detective's focus P1, P2, T? compared to the table focus P2, T4, C1 yields:  
EQ = 1 (for P2), EQT = 1 (for T?), NE = 2 (for P1, C1).

== Personage Interrogation (interrogation)


In addition to searching any open personage, a detective can also *interrogate* them to obtain clues. The result of an interrogation can be not only witness testimonies, but also physical clues — it is assumed that as a result of the interrogation, the personage handed something over to the detective.

During an interrogation, the detective "asks" the personage about facts *known* to the investigation (*open* key entities) or about investigation hypotheses (about any entity types) — that is, defines the detective's *interrogation focus*.  
If the personage "knows" anything about this, a clue linked to the focus is discovered.

The interrogation mechanic is designed so that without knowing the key entities or their types, it is difficult for a detective to discover a relevant target clue.

When answering, a personage may *"tell an untruth"* — a clue is discovered that is actually completely unrelated to the key entities in the interrogation focus (a *falsity* clue). The script regulates the number of "falsity" clues. The falsity of a clue can only be established through deductive analysis.  
The script's answers list which clues were indeed false.

Each personage is to some extent reluctant to share certain information, and the detective uses psychological pressure to get maximum information.  
This interaction is random in nature and is modeled using a D12 roll.

Interrogating a personage costs a certain amount of resource. A detective can be awarded points for an interrogation.

The script defines an *"Interrogation"* connection table, which determines the parameters for discovering clues during interrogation.

Interrogation procedure:

1. Based on the clues known from the investigation and logical conclusions, the detective selects a personage to interrogate, for example, P1.
2. Specifies the detective's focus — a set of IDs of any *open* entities or any types, for example, L1, P?.
3. Rolls a D12 to model psychological pressure on the personage.
4. The interrogation result is determined using the interrogation table.  
   Access to the interrogation table is provided through the Master Program.

=== Example of an "Interrogation" Table

|===
|Focus             |Threshold |Clue
|P2, L3, C4, C5, T2| 3.0      |C3
|C4, T5, T6        | 5.0      |C12
|P5                | 5.2      |C15
|===

----
  Clue C3 is linked to personage P4, and C12/15 to P1.
----

*Focus* — the table interrogation focus (same as <<search-focus, table search focus>>).

====
A restriction is placed on the detective's focus:  

*Among the elements of the detective's focus, there must be at least one ID of an open entity.*
====

*Threshold* — the threshold of resistance to the detective's psychological pressure.  
A _real_ number that is compared with the roll on the D12 dice.  
If the roll is less than the "Threshold," it is considered that the detective failed to overcome the personage's reluctance to share information, and therefore the target clue is not discovered.  
In the script, the detection threshold is set so that the clues most important to the investigation have higher threshold values. The ability to specify fractional values allows for "fine-tuning" the ordering of clues.

To reduce the influence of randomness, low threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the target clue of the personage, which is discovered upon a successful interrogation.  
A clue may be intentionally set as false by the script — simulating that the personage is lying / forgot.

=== Interrogation Cost, Point Scoring

*Interrogation cost* — the resource cost of interrogating any personage is the same and is defined in the script.  
Determines how much resource is spent to interrogate a personage. The detective learns the cost at the beginning of the game.

*Interrogation points* — the base number of points that can be awarded to a detective for interrogating a personage.  
The same base number of points is defined for all personages in the script.  
Base points are awarded for discovering a target clue during interrogation (whether false or not).  
When base points are awarded (if the clue is discovered), one additional point is granted for each matching _entity_ in the focus.

=== Algorithm for Determining the Target Clue in the Personage Interrogation Table

The algorithm for determining the target clue pursues the following goal: to identify the personage's clue that best matches the detective's focus, while ensuring clues are revealed starting from the least significant for the investigation.

The algorithm considers the rows of the interrogation table pertaining to the selected personage.  
Rows for which the clue has already been discovered in previous interrogations are excluded from consideration.

1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus match weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", and minimum *Threshold* is found.
3. If "EQ = 0" for this row, the personage does not know what the detective is asking about. The target clue is not discovered.  
   It is reported that the personage lacks the required information:
   * Non-matching entity IDs and types from the detective's focus.
   * Entity types of non-matching IDs in the table focus (as a hint at other connections).
====
For example, for the detective's focus "L3, P?, T?" and table focus "L4, T1, C2", the output will be:  
"Personage P1 does not know about L3, P?, but hints that they know about L?, T?, C?".
====

[start=4]
4. If "EQ > 0", the personage knows what the detective is asking about.  
   The following are selected for the message:
   * Matching entity IDs and types in the detective's focus.
   * Entity types of non-matching IDs in the table focus.

5. If "D12 >= Threshold", the target clue is discovered. The discovery of the clue and connections are reported:

====
For example, for target clue C8, detective's focus "L3, P?, C?", and table focus "L3, P7, P4, T2", the output will be:  

"Personage P1 knows about L3, P?, P?, T? connected to C8".  
====

It is reported how many points are awarded to the detective.
The row corresponding to the target clue is excluded from further interrogations.  

If all clues of a personage are discovered, an "All Clues Discovered" token is placed on the personage card. Further interrogations of the personage are impossible.

[start=6]   
6. If "D12 < Threshold", the target clue is not discovered. Only the connections are reported:  
"Personage P1 knows about L3, P?, P?, T?, but did not want to share details".

== Examination (examination)

An examination is any procedural action to establish connections between *open* entities that have no direct references to each other. For example: determining whether ash found in a location matches cigarettes found on a personage; conducting a ballistic examination; hacking a digital storage device, etc.

When conducting an examination, there are random factors that affect its outcome.  
This influence is modeled by a D12 roll.

An examination costs a certain amount of resource. A detective can be awarded points for an examination.

The script defines an *"Examination"* connection table, which determines the connection between entities.

Examination procedure:

1. The detective specifies the detective's focus — a set of IDs of any *open* entities or any types, for example, C1, P?.
2. Rolls a D12 dice to model the influence of random factors.
3. The examination result is determined using the "Examination" table.  
   This table is accessible only through the Master Program.
4. Upon completion of the examination, an "Expert Report" card is filled out, indicating the examination results.

=== "Examination" Connection Table

|===
|Focus          |Threshold|Clue
| P2, L3, L5, T6|10.0     | C2
| P3, C3, C4    |7.1      | C4
|===

*Focus* — the table examination focus (same as <<search-focus, table search focus>>).

====
A restriction is placed on the detective's focus:  

*Among the elements of the detective's focus, there must be at least two IDs of open entities.*
====

*Threshold* — the threshold of influence of random factors on the examination.  
A _real_ number that is compared with the roll on the D12 dice.  
If the roll is less than the "Threshold" number, it is considered that the negative influence of factors is significant, the examination was conducted poorly, and the target clue is not discovered.  
In the script, the influence threshold is set so that the clues most important to the investigation have higher threshold values. The ability to specify fractional values allows for "fine-tuning" the ordering of clues.

To reduce the influence of randomness, low threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the target clue, essentially an expert report detailing the connection.  
For example: "The discovered fingerprints match."

=== Examination Cost, Point Scoring

*Examination cost* — the resource cost of any examination is the same and is defined in the script.  
Determines how much resource is spent to conduct an examination. The detective learns the cost at the beginning of the game.

*Examination points* — the base number of points that can be awarded to a detective for an examination.  
The same base number of points is defined for all examinations in the script.  
Base points are awarded to the detective for discovering a clue.  
When base points are awarded (upon discovering a clue), one additional point is granted for each matching _entity_ in the focus.

== Algorithm for Identifying a Connection Row in the Examination Table

The algorithm for determining a connection pursues the following goal: to determine the presence of a connection and additional data for entities that best match the detective's focus and the D12 roll.

Rows for which the target clue was discovered in previous examinations are excluded from consideration.

[[expertise-quality]]  
1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus match weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", and minimum *Threshold* is found.
3. If "EQ = 0", no connections are identified. The target clue is not discovered.  
Failure to identify a connection is reported:
   * Non-matching entity IDs and types from the detective's focus.
   * Entity types of non-matching IDs in the table focus (as recommended).
====
For example: "Connection between L2, P4, C? not identified. Investigation of L?, P?, T? is recommended."
====

[start=4]
4. If "EQ = 1", connections are identified for one entity. The target clue is not discovered. Connections are reported "in general":
   * Matching entity IDs in the detective's focus.
   * Entity types in the table focus, excluding those matching IDs from the detective's focus.

====
For example, for the detective's focus "L2, L3, P?" and table focus "L2, L4, P1, T3":  

"Connection identified between L2 and L?, P?, T?".
====

[start=5]
5. If "EQ > 1", a connection is detected.  
The following are prepared for the message:

   * Matching entity IDs in the detective's focus.
   * Entity types in the table focus, excluding those matching IDs from the detective's focus.

[start=6]
6. If "D12 >= Threshold", the influence of factors is low, and the target clue is discovered.  

====
Message about connection detection and clue discovery (expert report):  
   "Connection detected between L2, P4 and L?, T?, P?. Expert report C3".  
   It is reported how many points are awarded to the detective.
====

The row with the discovered clue is excluded from further examinations.  

If target clues are discovered for all rows of the examination table, an "Examination Unavailable" token is placed. Further examinations are impossible.

[start=7]
7. If D12 < Threshold, the influence of factors is high, and the target clue is not discovered.  

====   
It is reported: "Connection detected between L2, P4 and L?, T?, P?. Conducting the examination was difficult".
====

== Focus Statistics

Obtaining table focus statistics is an optional mechanic; the ability to use it is regulated in the script.  
Obtaining statistics may be allowed to reduce the game's difficulty for beginners.

Obtaining focus statistics can be either free or cost a certain amount of resource (indicated in the script).

Statistics are calculated at the moment of request — rows for which target clues have already been discovered are not taken into account.

[[location-glue-hint]]  
=== Search Statistics

Before conducting a search, a detective can request the current search statistics:

1. The percentage of each entity type in all table search focuses is calculated.
2. Statistics are output: "Possible entity connections with P 45%, L 30%, T 25%, C 0%".

[[personage-glue-hint]]  
=== Interrogation Statistics

Before conducting an interrogation, a detective can request the current interrogation statistics:

1. The percentage of each entity type in all table interrogation focuses is calculated.
2. Statistics are output: "Personage may know about P 45%, L 30%, T 25%, C 0%".

[[expertise-glue-hint]]  
=== Examination Statistics

Before conducting an examination, a detective can request the current examination statistics:

1. The percentage of each entity type in all table examination focuses is calculated.
2. Statistics are output: "Examination can determine connections between P 45%, L 30%, T 25%, C 0%".

== Regulating the Influence of Randomness

To reduce the influence of the randomness factor (D12), players can specify a randomness influence factor (*rand factor*) when launching a script in the Master Program. This is a coefficient taking values from 0.0 to 1.0, by which the table clue discovery thresholds are multiplied. 

At a value of 0.0, the randomness factor is completely eliminated. At a value of 1.0, the randomness factor remains at the level intended by the script.

== Balance of Search, Interrogation, and Examination Mechanics

A search always yields a clue: if the roll fails, "Accidental Discovery" triggers and the clue with the lowest threshold is discovered. Interrogation and examination do not discover a clue upon failure. If searching is cheaper and yields key clues, it might be advantageous to search everything first, which could devalue interrogation/examination. To avoid such a mechanic imbalance, script parameters should be set as follows: searching should not be the cheapest source of key clues; interrogation and examination must be cost-competitive; the budget should not allow searching everything with plenty left over for interrogations; key IDs should be distributed among actions; falsity clues with low thresholds should be placed in locations so that accidental discovery yields "noise" or minor clues.

== Reusing Entities, Reference and Custom Entities

A script can use some entities from other (*reference*) scripts.
To do this, the script lists these entities in the exact form in which they are defined in the reference script (as regular script entities), with a note indicating which script they were borrowed from.  
Such entities are called *reference* entities.

All entities in the script that are not reference entities are considered *custom entities* (local entities of the script) and are printed before the game begins.
Cards for reference entities are taken from the reference scripts (if they were printed earlier) or are also printed.

== Reusing Entity Images

In the script, to reuse entity images (most often clues, witness testimonies, and examination conclusions), for each entity, you can specify the ID of the entity whose image will be used for this entity (asset).

== Answers

After completing the investigation, the detectives formulate their conclusions. 
Then, using the Master Program, the "answers" from the script are displayed.

====
 For example:
 
* Plot of the crime;
* Personage/location logs;
* What specific clues actually *lead* to;
* Hidden locations, ways, personages.   
====

The investigation's conclusions are compared with the answers. A decision is made on the success of the investigation.
