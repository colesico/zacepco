== About the document

The document describes the mechanics of a detective game and defines the general rules according to which it should be built.  
For the integrity of the game, an integral addition to these mechanics are *crime scenarios*, which describe the plot component.  
The mechanics itself is essentially a *framework* for a deductive detective game with elements of randomness.

== Crime scenario

A scenario within the mechanics describes a crime that has already occurred.  
During the game, players (detectives) must solve this crime.  
The scenario focuses on different degrees of difficulty in solving the crime, describing, for example, one crime or several at once, with one or several criminals, with or without accomplices, with different numbers of suspects, duration of the crime, size of the "theater of operations", etc.

Any scenario contains:

* Instructions for preparation before the investigation begins.
* Information for the course of the investigation.
* An "Answers" section, which can be viewed at the end of the game.

Ready-made scenarios come with the game or are generated by a special program.

The game takes place according to the scenario chosen by the players and is divided into two *phases*.

In the first phase, players, according to the scenario, perform preparatory actions before the investigation begins: assembling the game board, etc.

The second phase is the investigation, a cooperative process of solving the crime by detectives.

At the end of the game, the investigation's conclusions are compared with the scenario's "Answers" section.

== Master program

To moderate the game process, a computer program is used — the *"Master program"*, which is configured by the scenario for a specific game.  
The program also automates all calculations related to the game process and controls the game mechanics.

== Game entities and relations

The scenario operates with the following types of *game entities*:

* *Character (P)* — an actor in the crime;
* *Location (L)* — part of the crime scene;
* *Clue (C)* — part of information about the crime;
* *Time (T)* — a moment in time during the crime.

The game entities themselves (except time) are represented by entity cards.  
Each such card, depending on the entity type, has its own format.  
An entity is identified by a unique identifier consisting of a letter — the entity type — and a unique number. For example P2, L5, C55.

Time has no cards of its own, only an ordinal number (T1, T2, ...).

Each of the game entities can be linked by the scenario to any other entities.  
From the point of view of a relation, when one entity references another, the first is called the *key entity*, and the second is the *target entity*.

The scenario defines a set of game entities and their relations, which essentially describes the crime (defines the crime model).

Some of these entities and relations may not relate to the crime and may serve to complicate the investigation process (false clues).

Before the investigation begins, detectives know some small part of the entities and their relations.  
During the investigation, detectives gradually uncover the remaining entities and relations.

In the game, entities are represented by cards. Some of the entity cards used in the scenario are already ready-made — *"reference entities"*, while some require manufacturing — *"custom entities"*. They are present as templates in the scenario and must be printed independently before the game. Reference entities can be reused in different scenarios; if necessary, the scenario defines custom entities.

== Uncovering entities and relations

The game uses a mechanic of *gradual* uncovering by detectives of entity cards and discovery of relations between them.

Based on some already uncovered key entities, detectives can learn their relations with other target entities, both uncovered and not yet uncovered.  
Then they choose other key entities and again determine subsequent target entities and relations, and so on.

Relations of entities, depending on the specific game mechanics, are described by the scenario in the form of *relation tables* of a certain format.

When receiving information from relation tables, in order not to reveal all information about the crime to detectives at once, the *Master program* is used.

== Element of randomness

D12 die.

== Resource, points

In the game, each detective action costs a certain *resource*.  
If the action is successful, the player is awarded *points*.  
The scenario determines the total *budget* of the resource for the investigation.  
When the budget is exhausted, the investigation stops, detectives must draw conclusions from the available data and compare the results with the answers.

The individual number of earned points determines the best detective in the investigation.

== Game time

The crime scenario covers some time interval.  
Time in this interval flows discretely, in *ticks*, from the first to the last (T1, T2,...Tn).  
The crime lasts a number of ticks specified in the scenario.  
The more ticks, the harder it is to solve the crime.  
All events in the crime are tied to ticks.  
Something happens in each time tick.  
It is considered that nothing happens between ticks.

== Crime scene, locations, passages

In the scenario, the crime scene is defined as a graph.  
In the preparation phase before the investigation, players, based on this graph, assemble the crime scene — the stage — from individual *locations* (graph nodes). The stage is a grid of a certain size (the grid size is specified by the scenario). A location is placed in any cell of the stage grid. Some cells of the stage may be left empty.

Each location is represented by a square location card (reference or custom). The location card contains the following information:

* ID;
* Name;
* Description;
* Image of the location.

Adjacent locations can be connected to each other by *passages* for a character.  
If non-adjacent locations need to be connected by a passage, passage cards with different configurations (straight, turn, T-shaped) are used, which are laid out in empty cells of the stage, connecting the required locations.  
Nothing ever happens in a passage itself; it only serves to indicate the possibility of characters moving between locations.  
If it is necessary to model a character's behavior in a passage (for example, travel time, some actions), then it is replaced by a full-fledged location.

The scenario may also assume the presence of *"hidden" passages* between locations, which are not marked during the preparation phase.  
Detectives learn about the existence of such passages during the investigation.  
When a clue is uncovered in some location that indicates the presence of a hidden passage (*hidden passage clue*), the ID of the target location to which the passage leads is determined.  
A passage card is placed on the stage connecting the location in which the hidden passage clue was uncovered with the target location.

A hidden passage may lead to a *hidden location*.  
This is a location that detectives do not know about before the investigation begins.  
A hidden location is one of the *reference* locations not yet placed on the stage.  
A discovered hidden location is placed on the stage in the cell specified in the scenario.  
The location is connected by a passage to the location where the hidden passage clue was discovered.  
After being uncovered, the location becomes available for investigative actions.

Information about all hidden passages and locations is included in the scenario's *answers*.

When developing a scenario, locations must be defined in such a way that their meaning in the investigation is taken into account.  
For example, there may be no light in a cave, a character may enter a basement only with a key, a poisonous plant may grow in a conservatory, a bar operates from the 3rd to the 6th tick, etc.  
The semantic load and description of the location should help detectives in the investigation.

For each location, the scenario describes an event log (log) of that location for each time tick.  
The event in the log contains information about which characters were in this location, which clues they left or took from the location (clues that interacted with the location).

The event log is used at the end of the game when checking the investigation's conclusions and is unavailable to players during the investigation.

== Characters

An actor in the crime is a *character*.  
Each character is represented by a (reference or custom) character card.  
The character card contains the following information:

* ID;
* Name;
* Dossier (description);
* Image of the character.

The set of characters in the game is determined by the scenario.  
The scenario defines explicit characters — they are known before the investigation begins.  
Their cards are laid out next to the game board.

The scenario may also imply the presence of *hidden characters*.  
A hidden character is one whose card has not yet been laid out from the character deck openly on the table.  
A hidden character is one of the *reference* characters.

The presence of a hidden character can be determined during the investigation logically, based on discovered clues, or by uncovering a clue with a direct reference to this hidden character (similar to clues indicating a hidden passage).  
When a clue with a reference to a hidden character is discovered, their card is laid out from the character deck openly next to the game board with the cards of the other characters.  
After that, the character becomes available for investigative actions.

In the scenario, in the "Answers" section, all hidden characters are listed.

Characters in the scenario must be described in such a way that this description helps detectives in the investigation.

== Movements and actions of a character

Each character during the crime *at each tick* of time has only the following possibilities:

* Move to an adjacent location or remain in the current one.
* While in a location, perform some *one* action or do nothing.

Movement occurs to an adjacent location if there is a passage.  
On the scenario side, there may be some restrictions on the passage, for example a door that must be opened with a key.  
In general, a character may visit the same location several times in different ticks.  
For easier game variants, a character may visit a location only once.

The character's movement path (sequence of locations) is implied by the scenario but is not explicitly revealed to the players.  
Players can determine this path during the investigation.

Character paths are revealed by the scenario in the "Answers" section: for each character, their movements are indicated as a sequence of location IDs for each tick (in the character log).  
This information can be viewed at the end of the game.

During the investigation phase, to visualize the path (*track*) of a character's movement on the game board, tokens of the character's color are placed in locations.  
Each token has the number of the tick in which the character was in the location where the token lies.  
Such tokens are called character track tokens.

While in a location, a character may perform some *one* action.  
The action itself is not provided as an entity by the mechanics, but the result of this action becomes a *clue*, which is linked either to the location or to the character.

For each character, the scenario describes an event log (log) of that character for each time tick.  
The event in the log contains information about which location the character was in and which clue they interacted with (for example, left a trace or a trace remained on the character).

The event log is used at the end of the game when checking the investigation's conclusions and is unavailable to players during the investigation.

== Clues

A *clue* is a piece of information about the committed crime that detectives sequentially discover during the investigation.  
A clue can be some physical object, event, some information, fact.

Examples of clues: witness testimony, motive, note, cigarette butt, habit, character's addiction to smoking, fact of absence of an object in a location, expert report.

The crime scenario determines the set of clues involved in the game.  
A clue is represented by a (reference or custom) clue card with printed on it:

* ID;
* Name;
* Description (detailed);
* Image of the clue.

Some of the clues may be unrelated to the crime and serve to make the game more difficult (false clues). The more such clues, the harder the game.

Initially, clues are hidden from detectives.  
During the investigation, detectives gradually "uncover" clues — lay out clue cards openly.

If an uncovered clue contains references to other not yet uncovered entities, these entities are also uncovered (recursively). The scenario should not define deep recursion of uncovered entities.

Examples of clues:

* Clue C1: "Testimony. Saw character P1 (Maid) during the 4th tick in location L2 (Dining Room)".
* Clue C2: "A hidden passage to location L4 (Basement) was discovered in this location".
* Clue C6: "In this location C2 (Candlestick) is missing, but it was originally here".
* Clue C12: "Broken clock. The hand points to T8 ticks".
* Clue C13: "In this location character P1 (Gardener) was noticed at T3 tick with C6 (Knife) in hand".

== Variable values

To universalize printed entity cards, instead of concrete values/text, variable names are indicated in them, the values of which are determined in the scenario.

Example of using variables for a clue:

====
C1: Saw character $P during $T tick in location $L
====

The values P, T, L are taken from the scenario.

====
L2: Location $N. Description: $D
====

The name N and description D are taken from the scenario.

== Reuse of entities, reference and custom entities

A scenario may use some entities from other scenarios.  
To do this, the scenario indicates from which scenarios entities will be used. For these "imported" entities, "local" entities are created (as ordinary scenario entities), in which a reference to the imported entity is indicated.  
Such entities are called *reference*.

All scenario entities that do not have references to imported entities are considered *custom entities* (local scenario entities) and are printed before the game begins.

== Location search

During the investigation, detectives may *"search"* any uncovered location (including a previously hidden one) to try to uncover clues linked to that location.  
As a result of the search, with some probability a clue may be "discovered" (uncovered).

The scenario defines the relation table *"Location search"*, which determines the relation between locations and clues.  
During a search, the mechanic of probabilistic clue discovery is used together with the *"Search focus"* mechanic.  
Focus allows a clue targeted by the search focus to be discovered with greater probability and yields more points.  
However, the strategic goal of focus is rather not to "obtain" a clue, but to *formulate a hypothesis for testing*.  
Focus consists of two parts: table focus (reference) and detective focus.

Searching a location costs a certain resource. A detective may be awarded points for a search.

Search procedure:

1. The detective declares a search in a specific location, for example L1.
2. Indicates the detective focus — a set of IDs of any *uncovered* entities or any types, for example: T4, L?, C?.
3. Rolls a D12 die to model the probabilistic nature of clue discovery.
4. According to the "Location search" table, the search result is determined.  
   Access to the search table is carried out through the Master program.

=== Relation table "Location search"

|===
|Location |Focus           |Threshold|Clue
| L1     | P4, L3, L4, T4 |5.2  |C8
|  *     | L4, C5, C6     |5.0  |C3
| L5     |     L6         |8.0  |C12
|===

*Location* — ID of the searched location.

[[search-focus]]  
*Focus* — table search focus. It serves to increase the probability of uncovering clues that have relations with target entities of interest to detectives.  
In the table focus, only _IDs_ of entities related to the target clue are listed.  
Specifying individual types in the table focus is not allowed.  
You can list several IDs of the same type separated by commas — this is interpreted as any of them.

The detective focus may consist of one or several IDs of *uncovered* entities or any entity types.  
For example: "P1, C1, T?". The maximum number of elements in the detective focus is determined in the scenario (usually 3).

*Threshold* — the clue discovery threshold. A _real_ number that is compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold", negative factors are considered to have prevailed and the target clue is not discovered.  
In the scenario, the discovery threshold is set in such a way that the most important clues for the investigation have higher threshold values. The ability to specify fractional values allows clues to be "finely" ordered.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — ID of the target clue. The card of the discovered clue is laid out openly. To mark the place where the clue was found, a token with the ID of the uncovered clue is placed on the location.

=== Search cost, awarding points

[[search-cost]]  
*Search cost* — the resource cost of a search is the same for all locations and is determined in the scenario.  
It determines how many resources are spent on a search in a location. The detective learns the cost at the beginning of the game.

[[search-points]]  
*Points for search* — the base number of points that can be awarded to a detective for searching a location.  
For all locations in the scenario, the same base number of points is determined.  
Base points are awarded for uncovering a clue, but only if it was _NOT_ *<<accidental-discovery, accidentally discovered>>*.  
When awarding base points, one additional point is awarded for each match of an _entity_ in the detective focus with the table focus.

== Algorithm for determining the target clue in the location search table

Purpose of the algorithm: to determine the clue most corresponding to the detective focus and the D12 roll.

The algorithm considers only the rows of the search table relating to the selected location.  
Rows for which the clue has already been uncovered in previous searches are excluded from consideration.

1. For each row, focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculation of focus correspondence weights>>).
2. The table rows are ordered by descending "EQ", descending "EQT", ascending "NE", descending *Threshold*.
3. Sequentially, starting from the first row, the "Threshold" is compared with the number on the D12 die.
4. If the D12 value >= "Threshold", the review stops. The clue is discovered, it is uncovered.  
   It is reported how many points are awarded to the detective.

[start=5]
[[accidental-discovery]]  
5. If no suitable row is found (the D12 value is insufficient), *"Accidental discovery"* of a clue occurs.  
   The clue with the lowest threshold among the considered (not yet uncovered) clues is uncovered.  
   It is reported that a suspicious clue was accidentally discovered.
6. It is reported which elements (entities + types) of the _detective focus_ match the table focus of the uncovered clue:
   * Matched entity IDs and types in the detective focus;
   * Types of non-matched entity IDs in the table focus.

====
For example, for the detective focus "P2, T4, C?" and table focus "P1, P2, T4, L2", the following will be output:  
"In location L1, clue C2 was found, related to P2, T4, P?, L?".
====

[start=7]
7. If all clues of the location are uncovered, a token "All clues discovered" is placed on the location. Further searches of the location are impossible.

[[focus-weights-comp]]  
=== Calculation of focus correspondence weights

The following values of focus correspondence weights between the detective and table focuses are calculated:

* EQ = [number of matched entity IDs in the focuses],
* EQT = [number of matched types in the focuses],
* NE = [number of *NON*-matched entities or types] in the detective search focus and the table focus.

First, "EQ" is calculated by comparing IDs in both focuses. Then the matched IDs are excluded from both focuses.  
To calculate "EQT", the entity types directly indicated in the detective focus (P?, L?, ...) are compared with the types of the remaining IDs in the table focus. Elements matched during "EQT" calculation are excluded from both focuses.  
"NE" is calculated as the total number of remaining entities in the focuses.

When calculating "EQT", a type element "X?" in the detective focus is considered matched with an entity of the table focus (with an ID) if the type "X?" corresponds to the type in the entity ID.

For example, the detective focus P1, P2, T? in comparison with the table focus P2, T4, C1 gives:  
EQ = 1 (for P2), EQT = 1 (for T?), NE = 2 (for P1, C1).

== Character interrogation

The scenario associates some clues with each character.  
It is considered that some of them were with the character before the crime (for example, clothing, personal items, character).  
Some they received during the crime — picked up in locations or received from other characters (for example, a knife, a note).  
Some clues of a character describe their inherent traits (for example, habits, addiction to alcohol, character, etc.). The rest of the clues are the character's witness testimony.  
The scenario also assumes that during the crime characters may leave clues in locations, pass them to or plant them on other characters when meeting them in the same location.

Some of a character's clues may be known to detectives (for example, clothing, etc.) before the investigation.  
Another part of the clues is hidden.

Similar to the location search procedure, to uncover such clues related to a character, a detective may *"interrogate"* any uncovered character (including a previously hidden one).  
As a result of the interrogation, another character clue may be uncovered and a relation to other clues may be established.

During interrogation, the detective "asks" the character about facts known to the investigation (uncovered key entities) or about the investigation's hypotheses (about any types of entities) — that is, determines the *interrogation focus*.  
If the character "knows" something about this, a clue related to the focus and its relations are uncovered.  
The interrogation mechanic is built in such a way that it is difficult for a detective to uncover a relevant target character clue without knowing key entities or their types.

In their answer, the character may *"tell a lie"* — a clue is uncovered that is in fact in no way related to the key entities in the interrogation focus.  
The scenario regulates the number of "false" clues. The falsity of a clue can be established only through deductive analysis.  
The "Answers" section lists which clues were actually false.

Each character, to one degree or another, does not wish to share certain information, and the detective uses psychological pressure to obtain maximum information.  
This interaction has a random character and is modeled with a D12 roll.

Interrogating a character costs a certain resource. A detective may be awarded points for an interrogation.

The scenario defines the relation table *"Character interrogation"*, which determines the relation between characters and clues.

Interrogation procedure:

1. The detective chooses the character to interrogate, for example P1.
2. Indicates the detective focus — a set of IDs of any *uncovered* entities or any types, for example L1, P?.
3. Rolls D12 to model psychological pressure on the character.
4. According to the interrogation table, the interrogation result is determined.  
   Access to the interrogation table is carried out through the Master program.

=== Relation table "Character interrogation"

|===
|Character |Focus             |Threshold |Clue
|P1       |P2, L3, C4, C5, T2| 3.0  |C3
|P4       |C4, T5, T6        | 5.0  |C12
| *       |P5                | 5.2  |C15
|===

*Character* — the interrogated character.  
Based on clues known from the investigation and logical conclusions, the detective chooses the character to interrogate.

*Focus* — table interrogation focus (the same as <<search-focus, table search focus>>).

A restriction is imposed on the detective focus:  
*Among the elements of the detective focus there must be at least one entity ID.*

*Threshold* — threshold of resistance to the detective's psychological pressure.  
A _real_ number that is compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold", it is considered that the detective could not overcome the character's unwillingness to share information, and therefore the target clue is not uncovered.  
In the scenario, the discovery threshold is set in such a way that the most important clues for the investigation have higher threshold values. The ability to specify fractional values allows clues to be "finely" ordered.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the target clue of the character, which is uncovered upon successful interrogation.  
The clue may be intentionally specified incorrectly by the scenario — an imitation of the character lying / forgetting.

=== Interrogation cost, awarded points

*Interrogation cost* — the resource cost of interrogating any characters is the same and is determined in the scenario.  
It determines how much resource is spent per character interrogation. The detective learns the cost at the beginning of the game.

*Points for interrogation* — the base number of points that can be awarded to a detective for interrogating a character.  
For all characters in the scenario, the same base number of points is determined.  
Base points are awarded for uncovering the target clue during interrogation (false or not).  
When awarding base points, one additional point is awarded for each match of an _entity_ in the focus (regardless of whether the clue is uncovered).

[[interrogation-alg]]  
=== Algorithm for determining the target clue in the character interrogation table

The algorithm for determining the target clue pursues the following goal: to determine the character clue most corresponding to the detective focus, but at the same time clues should be revealed starting from the least significant for the investigation.

The algorithm considers the rows of the interrogation table relating to the selected character.  
Rows for which the clue has already been uncovered in previous interrogations are excluded from consideration.

1. For each row, focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculation of focus correspondence weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", and minimum *Threshold* is found.
3. If for this row "EQ = 0", the character does not know what the detective is asking about. The target clue is not uncovered.  
   It is reported that the character has no needed information:
   * Non-matched entity IDs and types from the detective focus.
   * Entity types of non-matched IDs in the table focus (as a hint at other relations).
====
For example, for the detective focus "L3, P?, T?" and table focus "L4, T1, C2", the following will be output:  
"Character P1 does not know about L3, P?, but hints that they know about L?, T?, C?".
====

[start=4]
4. If "EQ > 0", the character knows what the detective is asking about.  
   For the message, the following are selected:
   * Matched entity IDs and types in the detective focus.
   * Entity types of non-matched IDs in the table focus.

5. If "D12 >= Threshold", the target clue is uncovered. The uncovering of the clue and relations is reported:

====
For example, for the target clue C8, detective focus "L3, P?, C?" and table focus "L3, P7, P4, T2", the following will be output:

"Character P1 knows about L3, P?, P?, T?, related to C8".  
====

It is reported how many points are awarded to the detective.  
The row corresponding to the target clue is excluded from further interrogations.

If all character clues are uncovered, a token "All clues discovered" is placed on the character card. Further interrogations of the character are impossible.

[start=6]   
6. If "D12 < Threshold", the target clue is not uncovered. Only relations are reported:  
"Character P1 knows about L3, P?, P?, T?, but did not want to share details".

== Expertise

Expertise is any procedural action to establish relations between *uncovered* entities that do not have direct references to each other. For example, to determine whether the ash found in a location corresponds to the cigarettes found on a character, ballistic expertise, hacking a digital storage medium, etc.

During expertise, there are random factors that affect its result.  
This influence is modeled by a D12 roll.

Expertise costs a certain resource. A detective may be awarded points for expertise.

The scenario defines the relation table *"Expertise"*, which determines the relation between entities.

Procedure for conducting expertise:

1. The detective indicates the detective focus — a set of IDs of any *uncovered* entities or any types, for example C1, P?.
2. Rolls a D12 die to model the influence of random factors.
3. According to the "Expertise" table, the expertise result is determined.  
   This table is accessible only through the Master program.
4. Upon completion of the expertise, the card "Expert Report" is filled out, in which the expertise results are indicated.

=== Relation table "Expertise"

|===
|Focus          |Threshold|Clue
| P2, L3, L5, T6|10.0 | C2
| P3, C3, C4    |7.1  | C4
|===

*Focus* — table expertise focus (the same as <<search-focus, table search focus>>).

A restriction is imposed on the detective focus:  
*Among the elements of the detective focus there must be at least two entity IDs.*

*Threshold* — threshold of influence of random factors on expertise.  
A _real_ number that is compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold" number, it is considered that the negative influence of factors is significant, the expertise was performed poorly, and the target clue is not uncovered.  
In the scenario, the influence threshold is set in such a way that the most important clues for the investigation have higher threshold values. The ability to specify fractional values allows clues to be "finely" ordered.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — target clue, essentially an expert report detailing the relation.  
For example: "The discovered fingerprints match".

=== Expertise cost, awarded points

*Expertise cost* — the resource cost of any expertise is the same and is determined in the scenario.  
It determines how much resource is spent per expertise. The detective learns the cost at the beginning of the game.

*Points for expertise* — the base number of points that can be awarded to a detective for expertise.  
For all expertises in the scenario, the same base number of points is determined.  
Base points are awarded to the detective for uncovering a clue.  
When awarding base points, one additional point is awarded for each match of an _entity_ in the focus (regardless of whether the clue is uncovered).

== Algorithm for identifying a relation row in the expertise table

The algorithm for determining a relation pursues the following goal: to determine the presence of a relation and additional data for entities most corresponding to the detective focus and the D12 roll.

Rows for which the target clue was uncovered in previous expertises are excluded from consideration.

[[expertise-quality]]  
1. For each row, focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculation of focus correspondence weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", minimum *Threshold* is found.
3. If "EQ = 0", no relations are identified. The target clue is not uncovered.  
The failure to identify a relation is reported:
   * Non-matched entity IDs and types from the detective focus.
   * Entity types of non-matched IDs in the table focus (as recommendations).
====
For example: "The relation between L2, P4, C? was not identified. It is recommended to investigate L?, P?, T?".
====

[start=4]
4. If "EQ = 1", relations for one entity are identified. The target clue is not uncovered. Relations are reported "in general":
   * Matched entity IDs in the detective focus.
   * Entity types in the table focus, except those matched with IDs from the detective focus.

====
For example, for the detective focus "L2, L3, P?" and table focus "L2, L4, P1, T3":

"A relation of L2 with L?, P?, T? was identified".
====

[start=5]
5. If "EQ > 1", a relation is discovered.  
For the message, the following are prepared:

   * Matched entity IDs in the detective focus.
   * Entity types in the table focus, except those matched with IDs from the detective focus.

[start=6]
6. If "D12 >= Threshold", the influence of factors is low, the target clue is uncovered.  

====
Message about discovering a relation and uncovering a clue (expert conclusion):  
   "A relation of L2, P4 with L?, T?, P? was discovered. Expert conclusion C3".  
   It is reported how many points are awarded to the detective.
====

The row with the uncovered clue is excluded from further expertises.  

If for all rows of the expertise table the target clues are uncovered, a token "Expertise unavailable" is placed. Further expertise is impossible.

[start=7]
7. If D12 < Threshold, the influence of factors is high, the target clue is not uncovered.  

====   
It is reported: "A relation of L2, P4 with L?, T?, P? was discovered. The expertise was difficult to conduct".

====

[[focus-stat-hint]]  
== Focus statistics

Obtaining statistics of table focuses is an optional mechanic; the possibility of use is regulated in the scenario.  
Obtaining statistics may be allowed to reduce the difficulty of the game for beginners.

Obtaining focus statistics may be either free or cost a certain resource (indicated in the scenario).

Statistics are calculated at the moment of its request — rows for which target clues have already been uncovered are not taken into account.

[[location-glue-hint]]  
=== Location statistics

Before conducting a search, a detective may request the current statistics of a location:

1. The percentage of each entity type in all table focuses of the location is calculated.
2. Statistics are output: "Possible relations of the location with P 45%, L 30%, T 25%, C 0%".

[[personage-glue-hint]]  
=== Character statistics

Before conducting an interrogation, a detective may request the current statistics of a character:

1. The percentage of each entity type in all table focuses of the character is calculated.
2. Statistics are output: "The character may know about P 45%, L 30%, T 25%, C 0%".

[[expertise-glue-hint]]  
=== Expertise statistics

Before conducting expertise, a detective may request the current statistics of expertise:

1. The percentage of each entity type in all table focuses of expertise is calculated.
2. Statistics are output: "Expertise can determine relations between P 45%, L 30%, T 25%, C 0%".

== Direct relations of entities

A direct relation between any entities is possible through mention in a clue, as well as in the "Expertise" table.  
Relations are also defined according to the table:

|===
| |Location |Time |Clue |Character

|*Location* |Passages between locations| Clue |Discovery of a clue in a location| Clue
|*Time* | * |Adjacent ticks|Clue|Clue
|*Clue* | *  | *  |Clue| Discovery of a clue on a character
|*Character* | * | *  | *  |Clue
|===

== Answers

The "Answers" section is described in the scenario and revealed at the end of the game.  
The section consists of several subsections, each of which reveals certain aspects of the crime.  
Some answers are contained in the description of other entities, for example, which locations and passages are hidden, the falsity of clues, event logs, the importance of clues for the investigation, etc.

=== Description of the crime

The course of the crime, the locations involved, characters, and clues are briefly described in words.

=== Recommended investigation strategy

Recommended sequence of search, interrogation, expertise. Which clues to use, which to expect.
