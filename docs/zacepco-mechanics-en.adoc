== About the Document

The document describes the mechanics of a detective game and defines the general rules by which it should be built.  
For the integrity of the game, an integral addition to these mechanics are *crime scenarios*, which describe the plot component.  
The mechanics themselves are essentially a *framework* for a deductive detective game with elements of randomness.

== Crime Scenario

Within the mechanics, a scenario describes a crime that has already occurred.  
During the game, the players (detectives) must solve this crime.  
The scenario is designed for varying degrees of difficulty in solving the crime, describing, for example, a single crime or several at once, with one or several criminals, with or without accomplices, with different numbers of suspects, crime duration, size of the "theater of operations," etc.

Any scenario contains:

* Instructions for preparation before the investigation begins.
* Information for the course of the investigation.
* An "Answers" section that can be viewed at the end of the game.

Ready-made scenarios come with the game or are generated by a special program.

The game takes place according to the scenario chosen by the players and is divided into two *phases*.

In the first phase, the players, according to the scenario, perform preparatory actions to begin the investigation: assembling the game board, etc.

The second phase is the investigation, a cooperative process of solving the crime by the detectives.

At the end of the game, the investigation's conclusions are compared with the "Answers" section of the scenario.

== Master Program

To moderate the game process, a computer program is used — the *"Master Program"*, which is configured by the scenario for a specific game.  
The program also automates all calculations related to the game process and controls the game mechanics.

== Game Entities and Connections

The scenario operates with the following types of *game entities*:

* *Character ( P )* — an actor in the crime;
* *Location ( L )* — a part of the crime scene;
* *Clue ( C )* — a piece of information about the crime;
* *Time ( T )* — a moment in time during the crime.

The game entities themselves (except time) are represented by entity cards.  
Each such card has its own format depending on the entity type.  
An entity is identified by a unique identifier consisting of a letter — the entity type — and a unique number. For example, P2, L5, C55.

Time does not have its own cards, only an ordinal number (T1, T2, …).

Each of the game entities can be linked by the scenario to any other entities.  
From the perspective of a connection, when one entity references another, the first is called the *key entity*, and the second is the *target entity*.

The scenario defines a set of game entities and their connections, which essentially describes the crime (defines the crime model).

Some of these entities and connections may not relate to the crime and serve to complicate the investigation process (false clues).

Before the investigation begins, the detectives know a small portion of the entities and their connections.  
During the investigation, the detectives gradually discover the remaining entities and connections.

In the game, entities are represented by cards. Some of the entity cards used in the scenario are already prepared — *"reference entities"* — while others require manufacturing — *"custom entities"*. They are provided as layouts in the scenario and must be printed independently before the game. Reference entities can be reused in different scenarios; if necessary, the scenario defines custom entities.

== Discovering Entities and Connections

The game uses a mechanic of *gradual* discovery by the detectives of entity cards and detection of connections between them.

Based on some already discovered key entities, detectives can learn their connections to other target entities, both discovered and not yet discovered.  
Then they can choose other key entities and again determine further target entities and connections, and so on.

Depending on the specific game mechanics, entity connections are described by the scenario in the form of *connection tables* of a certain format.

When obtaining information from connection tables, to avoid revealing all information about the crime to the detectives at once, the *master program* is used.

== Element of Randomness

D12 die.

== Resource, Points

In the game, each detective action costs a certain *resource*.  
If the action is successful, the player is awarded *points*.  
The scenario defines the total *budget* of the resource for the investigation.  
When the budget is exhausted, the investigation stops, and the detectives must draw conclusions from the available data and compare the results with the answers.

The individual number of points earned determines the best detective in the investigation, provided that the detectives have solved the crime. If the detectives failed to solve the crime, the earned points are not counted.

== Game Time

The crime scenario covers a time interval divided into *ticks* (`T1, T2, … Tn`) — equal or unequal time intervals.

Each tick has a timestamp (date-time), for example `T4 = 21:30`. The timestamp defines the *right boundary* of the tick. Events of `T4` occur after the timestamp of the previous tick and no later than `21:30`. The scenario contains a publicly available "Timeline" table in which each tick is assigned a timestamp.
The difference between adjacent timestamps must be plausible: within one tick, a character must be able to perform the actions implied by the scenario.

All significant crime events occur in specific ticks; clues are tied to the time marks of ticks, not to time values within the tick itself. Even if, for example, for T3 = 21:00, T4 = 21:30, a clue indicates the time 21:20 — it is considered that the event occurred in tick T4, and it does not matter when exactly within the tick. The exact order of events within a tick is not defined and is not used for deduction, i.e., all events within a tick are consistent from the point of view of clues.

The more ticks, the harder it is to solve the crime.



In connection tables, focuses, and logs, only the tick number is used.



== Crime Scene, Locations, Connections

In the scenario, the crime scene is defined as a graph.  
In the preparation phase for the investigation, the players, based on this graph, assemble the crime scene — the stage — from individual *locations* (graph nodes). The stage is a grid of a certain size (the grid size is specified by the scenario). A location is placed in any cell of the stage grid. Some cells of the stage may be left empty.

Each location is represented by a square location card (reference or custom). A location card contains the following information:

* ID;
* Name;
* Description;
* Location image.

Two adjacent locations can be connected by *paths* that determine the possibility of a character moving between them.  
If two non-adjacent locations need to be connected, path cards with different configurations (straight, turn) are used, laid out one after another in empty cells of the stage, connecting the required locations.  
A path always connects only two locations. 

In the scenario, for movement along a path, certain restrictions or characteristics of the path can be specified in the form of a *description*. For example: a river, 10 meters wide. If the path description is absent, it is considered that for the investigation only the fact of the possibility of moving from one location to another is important.
Two locations can be connected by several paths with different restrictions/characteristics.

Nothing ever happens to characters on the path itself,  
if it is necessary to model any character actions while on the path, the path is replaced by a full-fledged location.

The scenario may also assume the presence of *"hidden" paths* between locations that are not indicated during the preparation phase for the investigation.  
Detectives learn about the existence of such paths during the investigation.  
When a clue indicating the presence of a hidden path (*hidden path clue*) is discovered in a location, the ID of the target location to which the path leads is determined.  
A path card is placed on the stage, connecting the location where the hidden path clue was discovered with the target location.

A hidden path may lead to a *hidden location*.  
This is a location that the detectives do not know about before the investigation begins.  
A hidden location is one of the *reference* locations not yet placed on the stage.  
A discovered hidden location is placed on the stage in the cell specified in the scenario.  
The location is connected by a path to the location where the hidden path clue was discovered.  
After discovery, the location becomes available for investigative actions.

Information about all hidden paths and locations is included in the scenario's *answers*.

When developing a scenario, locations and path descriptions should be defined in such a way that their meaning in the investigation is taken into account.  
For example, there may be no light in a cave, a character can enter a basement only with a key, a poisonous plant may grow in a greenhouse, a bar operates from the 3rd to the 6th tick, etc.  
The semantic load and description of locations and paths should help detectives in the investigation.

For each location, the scenario describes the event log (log) of that location for each time tick.  
The log event contains information about which characters were in this location and which clues appeared in the location (as a result of a character's actions).

The event log is used at the end of the game when checking the investigation's conclusions and is not available to players during the investigation.

== Characters

An actor in the crime is a *character*.  
Each character is represented by a (reference or custom) character card.  
A character card contains the following information:

* ID;
* Name;
* Dossier (description);
* Character image.

The set of characters in the game is determined by the scenario.  
The scenario defines explicit characters — they are known before the investigation begins.  
Their cards are placed next to the game board.

The scenario may also imply the presence of *hidden characters*.  
A hidden character is one whose card has not yet been placed from the character deck face up on the table.  
A hidden character is one of the *reference* characters.

The presence of a hidden character can be determined during the investigation logically, based on discovered clues, or by discovering a clue with a direct reference to that hidden character (similar to clues pointing to a hidden path).  
When a clue with a reference to a hidden character is discovered, their card from the character deck is placed face up next to the game board along with the cards of the other characters.  
After that, the character becomes available for investigative actions.

The scenario, in the "Answers" section, lists all hidden characters.

Characters in the scenario should be described in such a way that this description helps detectives in the investigation.

== Character Movement and Actions

For each character during the crime, *in each tick* of time Ti, there is only one of the following alternatives:

* Stay in the current location and do nothing.
* Stay in the current location and perform *one* *action*.
* Move to an adjacent location and do nothing.
* Move to an adjacent location and perform one action.

Movement occurs to an adjacent location if they are connected by a path.  
On the part of the scenario, there may be certain restrictions on the path, for example, a door that must be opened with a key.  
In the general case, a character can visit the same location several times in different ticks.  
For easier game variants, a character can visit a location only once.

The character's movement track (sequence of locations) is implied by the scenario but is not explicitly revealed to the players.  
Players can determine this track during the investigation.

Character tracks are revealed by the scenario in the "Answers" section: for each character, their movements are indicated as a sequence of location IDs for each tick (in the character log).  
This information can be viewed at the end of the game.

During the investigation phase, to visualize the character's movement path (*track*) on the game board, tokens of the character's color are placed in locations.  
Each token bears the number of the tick in which the character was in the location where the token lies.  
Such tokens are called character track tokens.

While in a location, a character can perform some *one* action.  
The action itself as an entity is not provided by the mechanics, but the result of this action becomes a *clue* that is linked either to the location, to the character, or to an expert examination.
 
   For example, a character saw another character. The first character acquires a clue in the form of witness testimony, which can be revealed during interrogation.

For each character, the scenario describes the event log (log) of that character for each time tick.  
The log event contains information about which location the character was in and which clue was generated by them (for example, left a trace in the location or a trace remained on the character).

The event log is used at the end of the game when checking the investigation's conclusions and is not available to players during the investigation.

== Clues

A *clue* is a piece of information about the committed crime that detectives sequentially discover during the investigation.  
A clue can be some physical object, event, some information, or fact.

Examples of clues: witness testimony, motive, note, cigarette butt, habit, a character's addiction to smoking, the fact that an item is missing from a location, expert report.

The crime scenario defines the set of clues involved in the game.  
A clue is represented by a (reference or custom) clue card with the following printed on it:

* ID;
* Name;
* Description (detailed);
* Clue image.

Some of the clues may be unrelated to the crime and serve to complicate the game (false clues). The more such clues, the harder the game.

Initially, clues are hidden from the detectives.  
During the investigation, detectives gradually "discover" clues — they place clue cards face up.

If a discovered clue contains references to other not yet discovered entities, those entities are also discovered (recursively). The scenario should not define deep recursion of discoverable entities.

Examples of clues:

* Clue C1: "Testimony. Saw character P1 (Maid) during the 4th tick in location L2 (Dining Room)."
* Clue C2: "A hidden passage to location L4 (Basement) was found in this location."
* Clue C6: "C2 (Candlestick) is missing from this location, but it was originally here."
* Clue C12: "Broken clock. The hand points to tick T8."
* Clue C13: "In this location, character P1 (Gardener) was noticed in tick T3 with C6 (Knife) in hand."

== Variable Values

To unify printed entity cards, instead of specific values/text, variable names are indicated on them, and their values are defined in the scenario.

Example of using variables for a clue:

====
C1: Saw character $P during tick $T in location $L
====

The values of P, T, L are taken from the scenario.

====
L2: Location $N. Description: $D
====

The name N and description D are taken from the scenario.

== Entity Reuse, Reference and Custom Entities

A scenario can use some entities from other scenarios.  
For this, the scenario specifies from which scenarios the entities will be used. For these "imported" entities, "local" entities are created (like ordinary scenario entities), in which a reference to the imported entity is specified.  
Such entities are called *reference*.

All scenario entities that lack references to imported entities are considered *custom entities* (local scenario entities) and are printed before the game begins.

== Location Search

During the investigation, detectives can *"search"* any discovered location (including previously hidden ones) to try to discover clues associated with that location.  
As a result of the search, with some probability, a clue may be "discovered" (revealed).

The scenario defines a connection table *"Location Search"*, which determines the relationship between locations and clues.  
During a search, the mechanic of probabilistic clue discovery is used together with the *"Search Focus"* mechanic.  
The focus allows for a higher probability of discovering the clue targeted by the search focus and for earning more points.  
However, the strategic goal of the focus is rather not to "obtain" a clue, but rather to *formulate a hypothesis for testing*.  
The focus consists of two parts: the table focus (reference) and the detective's focus.

Searching a location costs a certain resource. A detective may be awarded points for a search.

Search procedure:

1. The detective declares a search in a specific location, for example L1.
2. Specifies the detective's focus — a set of IDs of any *discovered* entities or any types, for example: T4, L?, C?.
3. Rolls a D12 die to model the probabilistic nature of clue discovery.
4. The search result is determined from the "Location Search" table.  
   Access to the search table is through the master program.

=== Connection Table "Location Search"

|===
|Location |Focus           |Threshold|Clue
| L1     | P4, L3, L4, T4 |5.2  |C8
|  *     | L4, C5, C6     |5.0  |C3
| L5     |     L6         |8.0  |C12
|===

*Location* — ID of the searched location.

[[search-focus]]  
*Focus* — table search focus. Serves to increase the probability of discovering clues that have connections to the target entities of interest to the detective.  
The table focus lists only _IDs_ of entities connected to the target clue.  
Specifying individual types in the table focus is not allowed.  
You can list several IDs of the same type separated by commas — this is interpreted as any of them.

The detective's focus may consist of one or more IDs of *discovered* entities or any entity types.  
For example: "P1, C1, T?". The maximum number of elements in the detective's focus is determined in the scenario (usually 3).

*Threshold* — clue discovery threshold. A _real_ number compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold", it is considered that negative factors came into play and the target clue is not discovered.  
In the scenario, the discovery threshold is set so that the clues most important for the investigation have higher threshold values. The ability to specify fractional values allows for "fine" ordering of clues.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — ID of the target clue. The discovered clue card is placed face up. To indicate the place where the clue was found, a token with the ID of the discovered clue is placed on the location.

=== Search Cost, Point Awarding

[[search-cost]]  
*Search cost* — the resource cost of a search is the same for all locations and is determined in the scenario.  
Determines how many resources are spent per search in a location. The detective learns the cost at the beginning of the game.

[[search-points]]  
*Search points* — the base number of points that can be awarded to a detective for searching a location.  
A single base number of points is defined for all locations in the scenario.  
Base points are awarded for discovering a clue, but only if it was _NOT_ *<<accidental-discovery, accidentally discovered>>*.  
When awarding base points, one additional point is awarded for each _entity_ match in the detective's focus with the table focus.

== Algorithm for Determining the Target Clue in the Location Search Table

The purpose of the algorithm: to determine the clue that best matches the detective's focus and the D12 roll.

The algorithm considers only the rows of the search table related to the selected location.  
Rows for which the clue has already been discovered in previous searches are excluded from consideration.

1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus matching weights>>).
2. The table rows are sorted by descending "EQ", descending "EQT", ascending "NE", descending *Threshold*.
3. Sequentially, starting from the first row, the "Threshold" is compared with the number on the D12 die.
4. If the D12 value >= "Threshold", the scan stops. The clue is discovered and revealed.  
   The number of points awarded to the detective is reported.

[start=5]
[[accidental-discovery]]  
5. If no suitable row is found (the D12 value is insufficient), *"Accidental Discovery"* of a clue occurs.  
   The clue with the lowest threshold among the considered (not yet discovered clues) is revealed.  
   It is reported that a suspicious clue was accidentally discovered.
6. The matching elements (entities + types) of the _detective's focus_ with the table focus of the discovered clue are reported:
   * Matched entity IDs and types in the detective's focus;
   * Types of unmatched entity IDs in the table focus.

====
For example, for the detective's focus "P2, T4, C?" and the table focus "P1, P2, T4, L2", the following will be output:  
"In location L1, clue C2 was found, connected with P2, T4, P?, L?".
====

[start=7]
7. If all clues of the location are discovered, a "All clues discovered" token is placed on the location. Further searches of the location are impossible.

[[focus-weights-comp]]  
=== Calculating Focus Matching Weights

The following focus matching weight values between the detective's and table focuses are calculated:

* EQ = [number of matched entity IDs in the focuses],
* EQT = [number of matched types in the focuses],
* NE = [number of *NOT* matched entities or types] in the detective's search focus and the table focus.

First, "EQ" is calculated by comparing IDs in both focuses. Then the matched IDs are excluded from both focuses.  
To calculate "EQT", the entity types explicitly specified in the detective's focus (P?, L?, …) are compared with the types of the remaining entity IDs in the table focus. Elements matched during the "EQT" calculation are excluded from both focuses.  
"NE" is calculated as the total number of remaining entities in the focuses.

When calculating "EQT", a type element "X?" in the detective's focus is considered matched with an entity in the table focus (with an ID) if the type "X?" corresponds to the type in the entity ID.

For example, the detective's focus P1, P2, T? compared with the table focus P2, T4, C1 gives:  
EQ = 1 (for P2), EQT = 1 (for T?), NE = 2 (for P1, C1).

== Character Interrogation

The scenario associates certain clues with each character.  
It is considered that some of them were with the character before the crime (for example, clothing, personal items, character).  
Some they acquired during the crime — picked up in locations or received from other characters (for example, a knife, a note).  
Some of a character's clues describe their inherent traits (for example, habits, addiction to alcohol, character, etc.). The remaining clues are the character's witness testimony.  
The scenario also assumes that during the crime, characters can leave clues in locations, pass them on, or plant them on other characters when meeting them in the same location.

Some of a character's clues may be known to detectives (for example, clothing, etc.) before the investigation.  
Another part of the clues is hidden.

Similar to the location search procedure, to discover such clues associated with a character, a detective can *"interrogate"* any discovered character (including a previously hidden one).  
As a result of the interrogation, another character clue may be discovered and a connection to other clues may be established.

During interrogation, the detective "asks" the character about facts known to the investigation (discovered key entities) or about the investigation's hypotheses (about any entity types) — that is, determines the *interrogation focus*.  
If the character "knows" something about this, a clue related to the focus and its connections are revealed.  
The interrogation mechanic is designed in such a way that it is difficult for a detective without knowledge of key entities or their types to reveal a relevant target character clue.

In response, the character may *"tell a lie"* — a clue is revealed that is actually in no way connected to the key entities in the interrogation focus.  
The scenario regulates the number of "false" clues. The falsity of a clue can only be established through deductive analysis.  
The "Answers" section lists which clues were actually false.

Each character, to one degree or another, does not want to share certain information, and the detective uses psychological pressure to obtain maximum information.  
This interaction has a random nature and is modeled using a D12 roll.

Interrogating a character costs a certain resource. A detective may be awarded points for an interrogation.

The scenario defines a connection table *"Character Interrogation"*, which determines the relationship between characters and clues.

Interrogation procedure:

1. The detective selects the character to interrogate, for example P1.
2. Specifies the detective's focus — a set of IDs of any *discovered* entities or any types, for example L1, P?.
3. Rolls D12 to model psychological pressure on the character.
4. The interrogation result is determined from the interrogation table.  
   Access to the interrogation table is through the master program.

=== Connection Table "Character Interrogation"

|===
|Character |Focus             |Threshold |Clue
|P1       |P2, L3, C4, C5, T2| 3.0  |C3
|P4       |C4, T5, T6        | 5.0  |C12
| *       |P5                | 5.2  |C15
|===

*Character* — the interrogated character.  
Based on the clues known from the investigation and logical conclusions, the detective chooses the character to interrogate.

*Focus* — table interrogation focus (the same as the <<search-focus, table search focus>>).

A restriction is imposed on the detective's focus:  
*Among the elements of the detective's focus, there must be at least one entity ID.*

*Threshold* — the threshold of resistance to the detective's psychological pressure.  
A _real_ number compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold", it is considered that the detective could not overcome the character's reluctance to share information, and therefore the target clue is not revealed.  
In the scenario, the discovery threshold is set so that the clues most important for the investigation have higher threshold values. The ability to specify fractional values allows for "fine" ordering of clues.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the target character clue that is revealed upon a successful interrogation.  
The clue may be intentionally specified incorrectly by the scenario — simulating that the character is lying / has forgotten.

=== Interrogation Cost, Points Awarded

*Interrogation cost* — the resource cost of interrogating any characters is the same and is determined in the scenario.  
Determines how much resource is spent per character interrogation. The detective learns the cost at the beginning of the game.

*Interrogation points* — the base number of points that can be awarded to a detective for interrogating a character.  
A single base number of points is defined for all characters in the scenario.  
Base points are awarded for revealing the target clue during interrogation (false or not).  
When awarding base points (if a clue is revealed), one additional point is awarded for each _entity_ match in the focus.

[[interrogation-alg]]  
=== Algorithm for Determining the Target Clue in the Character Interrogation Table

The purpose of the target clue determination algorithm is: to determine the character clue that best matches the detective's focus, but at the same time, clues should be revealed starting from the least significant for the investigation.

The algorithm considers the rows of the interrogation table related to the selected character.  
Rows for which the clue has already been revealed in previous interrogations are excluded from consideration.

1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus matching weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", and minimum *Threshold* is found.
3. If for this row "EQ = 0", the character does not know what the detective is asking about. The target clue is not revealed.  
   It is reported that the character has no relevant information:
   * Unmatched entity IDs and types from the detective's focus.
   * Entity types of unmatched IDs in the table focus (as a hint about other connections).
====
For example, for the detective's focus "L3, P?, T?" and the table focus "L4, T1, C2", the following will be output:  
"Character P1 does not know about L3, P?, but hints that they know about L?, T?, C?".
====

[start=4]
4. If "EQ > 0", the character knows what the detective is asking about.  
   For the report, the following are selected:
   * Matched entity IDs and types in the detective's focus.
   * Entity types of unmatched IDs in the table focus.

5. If "D12 >= Threshold", the target clue is revealed. The discovery of the clue and connections is reported:

====
For example, for the target clue C8, the detective's focus "L3, P?, C?" and the table focus "L3, P7, P4, T2", the following will be output:  

"Character P1 knows about L3, P?, P?, T?, connected with C8".  
====

The number of points awarded to the detective is reported.
The row corresponding to the target clue is excluded from further interrogations.  

If all character clues are revealed, a "All clues discovered" token is placed on the character card. Further interrogations of the character are impossible.

[start=6]   
6. If "D12 < Threshold", the target clue is not revealed. Only the connections are reported:  
"Character P1 knows about L3, P?, P?, T?, but did not want to share details."

== Expert Examination

An expert examination is any procedural action to establish connections between *discovered* entities that do not have direct references to each other.  For example: determine whether the ash found in a location matches the cigarettes found on a character; conduct a ballistic examination; crack a digital medium, etc.

During an expert examination, there are random factors that affect its result.  
This influence is modeled by a D12 roll.

An expert examination costs a certain resource. A detective may be awarded points for an expert examination.

The scenario defines a connection table *"Expert Examination"*, which determines the relationship between entities.

Expert examination procedure:

1. The detective specifies the detective's focus — a set of IDs of any *discovered* entities or any types, for example C1, P?.
2. Rolls a D12 die to model the influence of random factors.
3. The expert examination result is determined from the "Expert Examination" table.  
   This table is available only through the master program.
4. Upon completion of the expert examination, an "Expert Report" card is filled out, indicating the results of the expert examination.

=== Connection Table "Expert Examination"

|===
|Focus          |Threshold|Clue
| P2, L3, L5, T6|10.0 | C2
| P3, C3, C4    |7.1  | C4
|===

*Focus* — table expert examination focus (the same as the <<search-focus, table search focus>>).

A restriction is imposed on the detective's focus:  
*Among the elements of the detective's focus, there must be at least two entity IDs.*

*Threshold* — the threshold of influence of random factors on the expert examination.  
A _real_ number compared with the value rolled on the D12 die.  
If the roll is less than the "Threshold" number, it is considered that the negative influence of factors is significant, the expert examination was performed poorly, and the target clue is not revealed.  
In the scenario, the influence threshold is set so that the clues most important for the investigation have higher threshold values. The ability to specify fractional values allows for "fine" ordering of clues.

To reduce the influence of randomness, small threshold values should be specified; to eliminate randomness — less than 1.

*Clue* — the target clue, essentially an expert report detailing the connection.  
For example: "The discovered fingerprints match."

=== Expert Examination Cost, Points Awarded

*Expert examination cost* — the resource cost of any expert examination is the same and is determined in the scenario.  
Determines how much resource is spent per expert examination. The detective learns the cost at the beginning of the game.

*Expert examination points* — the base number of points that can be awarded to a detective for an expert examination.  
A single base number of points is defined for all expert examinations in the scenario.  
Base points are awarded to the detective for revealing a clue.  
When awarding base points (when a clue is revealed), one additional point is awarded for each _entity_ match in the focus.

== Algorithm for Identifying a Connection Row in the Expert Examination Table

The purpose of the connection determination algorithm is: to determine the presence of a connection and additional data for entities that best match the detective's focus and the D12 roll.

Rows for which the target clue has been revealed in previous expert examinations are excluded from consideration.

[[expertise-quality]]  
1. For each row, the focus weights EQ, EQT, NE are calculated (see <<focus-weights-comp, calculating focus matching weights>>).
2. The row with the maximum "EQ", maximum "EQT", minimum "NE", minimum *Threshold* is found.
3. If "EQ = 0", no connections are identified. The target clue is not revealed.  
The failure to identify a connection is reported:
   * Unmatched entity IDs and types from the detective's focus.
   * Entity types of unmatched IDs in the table focus (as recommended).
====
For example: "The connection between L2, P4, C? was not identified. Investigation of L?, P?, T? is recommended."
====

[start=4]
4. If "EQ = 1", connections for one entity are identified. The target clue is not revealed. Connections "in general" are reported:
   * Matched entity IDs in the detective's focus.
   * Entity types in the table focus, except those matched with IDs from the detective's focus.

====
For example, for the detective's focus "L2, L3, P?" and the table focus "L2, L4, P1, T3":  

"A connection of L2 with L?, P?, T? was identified."
====

[start=5]
5. If "EQ > 1", a connection is discovered.  
For the report, the following are prepared:

   * Matched entity IDs in the detective's focus.
   * Entity types in the table focus, except those matched with IDs from the detective's focus.

[start=6]
6. If "D12 >= Threshold", the influence of factors is low, and the target clue is revealed.  

====
Message about the discovery of a connection and the revealing of a clue (expert report):  
   "A connection of L2, P4 with L?, T?, P? was discovered. Expert report C3".  
   The number of points awarded to the detective is reported.
====

The row with the revealed clue is excluded from further expert examinations.  

If for all rows of the expert examination table the target clues are revealed, an "Expert examination unavailable" token is placed. Further expert examinations are impossible.

[start=7]
7. If D12 < Threshold, the influence of factors is high, and the target clue is not revealed.  

====   
It is reported: "A connection of L2, P4 with L?, T?, P? was discovered. The expert examination was difficult to perform."

====

[[focus-stat-hint]]  
== Focus Statistics

Obtaining statistics on table focuses is an optional mechanic; the possibility of use is regulated in the scenario.  
Obtaining statistics may be allowed to reduce the difficulty of the game for beginners.

Obtaining focus statistics can be either free or cost a certain resource (specified in the scenario).

Statistics are calculated at the time of the request — rows for which the target clues have already been revealed are not taken into account.

[[location-glue-hint]]  
=== Location Statistics

Before conducting a search, a detective may request the current statistics of a location:

1. The percentage of each entity type in all table focuses of the location is calculated.
2. The statistics are output: "Possible connections of the location with P 45%, L 30%, T 25%, C 0%".

[[personage-glue-hint]]  
=== Character Statistics

Before conducting an interrogation, a detective may request the current statistics of a character:

1. The percentage of each entity type in all table focuses of the character is calculated.
2. The statistics are output: "The character may know about P 45%, L 30%, T 25%, C 0%".

[[expertise-glue-hint]]  
=== Expert Examination Statistics

Before conducting an expert examination, a detective may request the current statistics of the expert examination:

1. The percentage of each entity type in all table focuses of the expert examination is calculated.
2. The statistics are output: "The expert examination can determine connections between P 45%, L 30%, T 25%, C 0%".

== Direct Entity Connections

A direct connection between any entities is possible through mention in a clue, as well as in the "Expert Examination" table.  
Connections are also defined according to the table:

|===
| |Location |Time |Clue |Character

|*Location* |Paths between locations| Clue |Discovery of a clue in a location| Clue
|*Time* | * |Adjacent ticks|Clue|Clue
|*Clue* | *  | *  |Clue| Discovery of a clue on a character
|*Character* | * | *  | *  |Clue
|===

== Answers

The "Answers" section is described in the scenario and revealed at the end of the game.  
The section consists of several subsections, each of which reveals certain aspects of the crime.  
Some of the answers are contained in the descriptions of other entities, for example, which locations and passages are hidden, the falsity of clues, event logs, the importance of clues for the investigation, etc.

=== Crime Description

The course of the crime, the locations involved, characters, and clues are briefly described in words.

=== Recommended Investigation Strategy

The recommended sequence of search, interrogation, expert examination. Which clues to use, which to expect.
